# V3 검증 "전체 게임 결과가 너무 적게 표시" 이슈 분석

## 1. 현상 정리

| 항목 | 값 |
|------|-----|
| grid_string | `bbbpbpppppbbbbpbbppbbpbpbbppbpbppbbpbbpppbbppbppbbbp` (52자) |
| 앵커 수 | 약 27개 (2,3,4,9,13,14,16,18,20,21,22,23,25,27,28,29,30,32,34,35,37,40,42,44,45,47,50) |
| 표시된 스텝 수 | **6개** |
| 총 예측 | 6 |
| 총 실패 | 2 |
| 스킵 | 0 |
| 정확도 | 66.7% |
| current_pos (종료 시) | 52 |

- 검증 앱과 라이브 게임 결과 **동일**
- 사용자 기대: 52자·27개 앵커 기준으로 **스텝이 더 많아야 함**

---

## 2. 원인 분석

### 2.1. V3 설계상의 특성

V3 요구사항:
- **[RULE-1]** 적중 시 즉시 종료 → 해당 앵커 검증 종료
- **[RULE-2]** 3회 연속 불일치 시 앵커 실패 → 다음 앵커로 이동

즉, 한 앵커당 **최소 1스텝(적중)** 또는 **최대 3스텝(3연속 실패)**까지만 검증하고 다음 앵커로 넘어간다.

따라서:
- 한 앵커에서 윈도우 9에서 맞으면 → 1스텝
- 여러 앵커에서 1스텝씩 적중 → 앵커당 1스텝만 기록

### 2.2. "6스텝"이 나오는 흐름 (추정)

적중 시 `current_pos = pos + 1`로 크게 점프하고, 다음 앵커는 `current_pos` 이후 첫 앵커만 선택한다.

예시 (anchors = [2,3,4,9,13,14,...]):
- Step 1: 앵커 2, pos 10 적중 → current_pos=11 → 다음 앵커 13
- Step 2: 앵커 13, pos 21 적중 → current_pos=22 → 다음 앵커 22
- Step 3: 앵커 22, pos 30 적중 → current_pos=31 → 다음 앵커 32
- Step 4: 앵커 32, pos 40 적중 → current_pos=41 → 다음 앵커 42
- Step 5,6: 앵커 42에서 pos 50, 51 검증 (예: 1적중 2실패 등)

→ 6번의 검증만으로 current_pos=52까지 도달 가능하다.

### 2.3. 이슈 후보

#### 후보 A: 문자열 끝 처리로 인한 조기 종료 (live_game)

**live_game `cold_start` 로직:**
```python
if pos >= len(grid_string):
    current_pos = len(grid_string)
    exited_string_end = True
    break  # for 탈출

# ... for 루프 끝난 후 ...
elif exited_string_end:
    break  # while 전체 탈출
```

`pos >= len`이 되면:
- 해당 앵커의 다음 윈도우는 아예 시도하지 않고
- while 전체를 빠져나와 **남은 앵커를 모두 건너뛴다.**

**예:** 앵커 42, pos 51까지 검증 후, window 11 시도 시 pos=52 ≥ 52 → break  
→ `exited_string_end = True` → while 종료 → 앵커 44,45,47,50은 검증하지 않음.

다만, 앵커 44~50은 `pos = anchor + 8`부터 시작하면 이미 52 이상이라 애초에 검증 불가하다.  
→ **이번 52자 입력에서는 live_game의 문자열 끝 처리만으로는 스텝 수가 줄어들었을 가능성은 낮다.**

#### 후보 B: 예측 테이블 커버리지

- `total_skipped = 0` → 시도한 6개 포지션에는 모두 예측이 존재
- 시도하지 않은 포지션은 `pos < current_pos` 또는 `pos >= len`로 인해 루프에서 제외됨
- 즉, **예측 부재 때문에 스킵된 것은 아님**

#### 후보 C: current_pos 점프로 인한 앵커 스킵

적중 시 `current_pos = pos + 1`이 되므로, 그보다 작은 앵커들은 모두 건너뛴다.

예:
- pos 10 적중 → current_pos=11 → 앵커 3,4,9는 검증하지 않음
- pos 21 적중 → current_pos=22 → 앵커 14,16,18,20,21은 검증하지 않음

V3 설계상 `current_pos` 이후 첫 앵커만 검증하므로, 이 동작 자체는 요구사항과 일치한다.

#### 후보 D: 앵커 44,45,47,50 미검증

| 앵커 | window 9 시 pos | 검증 가능 여부 |
|------|-----------------|----------------|
| 44   | 52              | 불가 (≥52)     |
| 45   | 53              | 불가           |
| 47   | 55              | 불가           |
| 50   | 58              | 불가           |

문자열 길이 52에서는 이 앵커들에 대해서는 윈도우 9~14 모두 `pos >= 52`가 되어 **검증할 포지션이 없다.**  
→ 스텝이 늘어날 여지가 없음.

## 3. 결론 및 추가 확인 사항

### 3.1. 현 시점 판단

- 52자·27개 앵커에서 6스텝이 나오는 것은 **V3 로직과 “첫 적중/3연속 실패 시 종료” 설계와는 모순되지 않음.**
- 검증 앱과 라이브 게임이 동일 결과를 내는 것은 로직이 일치한다는 의미로 해석 가능함.

### 3.2. 기대와의 차이

사용자가 “전체 게임 결과가 너무 적다”고 느끼는 경우, 다음 중 어떤 의미인지가 중요함:

| 기대 | V3 동작 | 비고 |
|------|--------|------|
| (1) 앵커당 최소 1회는 검증 | 적중 시 1회만 검증 후 다음 앵커 | 설계대로 |
| (2) 모든 앵커를 검증 | current_pos 점프로 일부 앵커 생략 | 설계대로 |
| (3) 모든 “예측 가능 포지션” 검증 | 적중 시 곧바로 종료 | 설계대로 |
| (4) 앵커당 윈도우 9~14 전부 검증 | 적중 시 즉시 종료 | V3 설계와 다름 |

- (1)~(3): 현재 구현이 V3 요구사항과 부합
- (4): 다른 검증 모드가 필요 (예: “전 윈도우 검증” 모드)

### 3.3. 추가로 확인할 점

1. **실제 기대 동작**
   - “전체 게임 결과”가 의미하는 것이 (1)~(3) 중 무엇인지, 또는 (4)인지
   - 앵커당 1~3스텝만 나오는 것이 문제인지, 아니면 특정 앵커가 아예 빠지는 것이 문제인지

2. **문자열 끝 처리 차이**
   - live_game: `pos >= len` 시 while 전체 종료
   - 모듈: `pos >= len` 시 for만 종료 후, 다음 앵커로 계속 진행
   - 앵커 44~50처럼 이미 검증 불가인 경우에는 영향 없지만, **더 긴 문자열**에서는 live_game에서만 조기 종료로 스텝이 줄어들 수 있음

3. **스텝 수 기대치**
   - 52자·27개 앵커 기준으로 대략 몇 스텝을 기대하는지
   - 예: “앵커 수와 비슷한 20~30 스텝” 등

## 4. 권장 조치

1. **요구 의미 확인**: “전체 게임 결과”가 (1)~(4) 중 어떤 것인지 구체화
2. **긴 문자열로 검증**: 100자 이상 등으로 테스트해 live_game 문자열 끝 처리에 따른 조기 종료 여부 확인
3. **로깅 추가**: 앵커 선택, `current_pos` 변화, `pos >= len` 발생 지점 등을 로그로 남겨 스텝 수가 결정되는 구간 파악
