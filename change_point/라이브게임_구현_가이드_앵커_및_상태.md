# 라이브게임 구현 가이드: 앵커 선택 두 방식 + 상태·주의사항

## 목적

- **전체 가설**에서 "다음에 쓸 앵커"를 정하는 방식이 **두 가지**라 정의가 흐릿해 혼선이 자주 발생함.
- 라이브게임에서 **라이브 값 업데이트**와 **다음 앵커 찾기**를 구현할 때마다 같은 종류의 이슈가 반복됨.
- 이 문서는 (1) 두 방식을 명확히 정의하고, (2) 어떤 흐름에서 어느 방식을 쓸지 정리하며, (3) **live_step 구현 시 체크리스트**를 두어 시행착오를 줄이는 것을 목표로 함.

---

## 1. "다음 앵커" 선택 방식 — 두 가지 정의

전체 가설(그리드 스트링 + 앵커 리스트)이 주어졌을 때, **현재 진행 위치**에서 **다음에 사용할 앵커**를 고르는 방법은 아래 두 가지로 구분한다.

### 방식 A: 위치 기준 (position-based, REQ-101 스타일)

- **문구**: "**진행 위치(current_pos / search_from) 이상인** 첫 앵커"
- **조건**: `anchor >= from_pos` 인 첫 앵커 (정렬된 `anchors`에서 `from_pos` 이상인 최소 인덱스).
- **구현**: `_first_anchor_from_position(anchors, from_pos)`  
  - `from_pos`는 보통 `current_pos` 또는 상태의 `search_from`.
- **의미**: "지금까지 검증이 끝난 **위치의 다음**부터 새로 앵커를 찾을 때, **앵커의 위치**가 그 기준 위치 이상인 첫 앵커를 쓴다."
- **사용처**: V3 hypothesis_module, cold_start 종료 후, live_step에서 **예측 수행 후** 정답/오답 처리 시 다음 앵커 계산.

### 방식 B: 예측 가능(커버리지) 기준 (coverage-based, 라이브 V4/V5 스타일)

- **문구**: "**특정 position을 (주어진 윈도우로) 예측할 수 있는** 앵커들 중 **가장 앞선** 앵커"
- **조건**: `anchor + (window_size - 1) >= position` 인 첫 앵커.  
  - 윈도우 9만 쓰면: `anchor >= position - 8` → "position을 예측하는 앵커" = `position - 8` (같으면 그 앵커, 없으면 그 이상 첫 앵커).
- **의미**: "다음에 **예측할 위치**가 정해져 있을 때, 그 위치를 **실제로 커버하는** 앵커 중 가장 낮은 앵커를 쓴다."
- **사용처**: 라이브게임에서 **스킵만 했을 때** "다음 예측 위치(next_pos)"에 대응하는 앵커를 정할 때. (예: freq518_win50의 스킵 분기에서 `anchor_for_next = next_pos - 8` 후 해당 앵커 인덱스 계산.)

### 요약 표

| 구분 | 방식 A (위치 기준) | 방식 B (예측 가능 기준) |
|------|---------------------|--------------------------|
| **기준** | `anchor >= from_pos` | `anchor + (ws - 1) >= position` |
| **함수** | `_first_anchor_from_position(anchors, from_pos)` | 윈도우 9일 때: `anchor_for_next = next_pos - 8` 후 인덱스 검색 |
| **언제** | 검증 종료 후 "다음부터 앵커 탐색" | "다음에 예측할 위치"에 맞는 앵커 선택 |
| **상태 변수** | `search_from` (탐색 시작 위치) | 보통 `next_pos`만으로 계산, search_from 유지 |

- **같은 라이브게임 안에서 A와 B를 둘 다 쓸 수 있음**:  
  - 스킵 시 → B로 "다음 예측 위치에 대응하는 앵커" 계산, `search_from`은 **변경하지 않음**.  
  - 정답/3연패 등 종료 조건 충족 시 → A로 `search_from = next_pos` 갱신 후 `_first_anchor_from_position(new_anchors, new_search_from)`.

## 2. 상태(state) 변수 정리

라이브게임 상태에 반드시 포함·일관되게 다뤄야 할 항목이다.

| 변수 | 의미 | cold_start 종료 시 | live_step에서 |
|------|------|---------------------|----------------|
| **current_pos** | 다음에 검증/예측할 위치 (보통 `len(grid_string)`와 동일하게 감) | 마지막으로 처리한 position + 1 | `next_pos = position + 1` 로 갱신 |
| **search_from** | "다음 앵커를 찾을 때 사용할 위치 기준" (방식 A의 `from_pos`) | `current_pos`로 설정 | 스킵 시 **유지**, 정답/3연패 시 **next_pos**로 갱신 |
| **active_anchor_idx** | 현재 사용 중인 앵커의 인덱스 | 방식 A로 계산한 인덱스 | 스킵/정답/오답 분기마다 명시적으로 계산해 설정 |
| **anchors** | 현재 그리드 스트링 기준 change-point 앵커 리스트 | `_anchors_from_grid_string(grid_string)` | 매 스텝 `_anchors_from_grid_string(new_grid_string)` 로 **재계산** |
| **anchor_failure_count** | 현재 앵커에서의 연속 실패 횟수 | 0 또는 유지 | 정답 시 0, 실패 시 +1, 3연패 시 0으로 리셋 후 다음 앵커 |

- **주의**: `search_from`은 **live_step의 모든 분기**에서 새 state를 만들 때 반드시 넣어야 한다.  
  - 스킵 분기에서는 "기존 search_from 유지"이므로, **그 분기 안에서** `search_from = state.get("search_from", state.get("current_pos", 0))` 처럼 **한 번은 읽어서 변수에 할당**한 뒤 `new_state["search_from"] = search_from` 해야 한다.  
  - 그렇지 않으면 "local variable 'search_from' where it is not associated with a value" 같은 오류가 난다.

## 3. live_step 구현 시 체크리스트

새 가설용 라이브게임을 만들거나 기존 live_step을 수정할 때, 아래를 한 번씩 확인하면 실수를 줄일 수 있다.

### 3.1. 분기 구성

- [ ] **에러 분기**: 입력이 b/p가 아닐 때 → state/history/grid_string 변경 없이 early return.
- [ ] **스킵 분기**: `skipped or predicted is None` 일 때  
  - [ ] `new_anchors = _anchors_from_grid_string(new_grid_string)`  
  - [ ] **다음 앵커**: 가설에 맞게 **방식 A 또는 B** 중 하나를 명시적으로 선택하고, 그에 맞게 `new_aidx` 계산.  
  - [ ] **search_from**: 이 분기에서는 보통 "유지". 반드시 `search_from = state.get("search_from", state.get("current_pos", 0))` 등으로 **값을 읽어서** `new_state["search_from"] = search_from` 에 넣기. (미할당 변수 참조 방지.)
  - [ ] `new_state`에 current_pos, active_anchor_idx, anchors, anchor_failure_count, next_window_size, search_from, 기타 가설 파라미터 모두 포함.
- [ ] **예측 수행 분기** (정답/오답):  
  - [ ] `search_from = state.get("search_from", state.get("current_pos", 0))` 를 **분기 진입 직후** 한 번 읽기.  
  - [ ] 정답 시: `new_search_from = next_pos`, 다음 앵커 = `_first_anchor_from_position(new_anchors, new_search_from)` (방식 A).  
  - [ ] 3연패 시: 동일하게 `new_search_from = next_pos`, 방식 A로 다음 앵커.  
  - [ ] 1~2연패 시: `new_search_from = search_from` 유지, 현재 앵커 인덱스만 새 anchors 기준으로 유지(또는 동일 앵커 값으로 인덱스 찾기).  
  - [ ] `new_state["search_from"] = new_search_from` 및 나머지 상태 필드 일괄 설정.

### 3.2. "다음 앵커" 계산 일관성

- [ ] **가설이 "위치 기준(REQ-101)"만 쓰는 경우**:  
  - cold_start, live_step 모두 `_first_anchor_from_position(anchors, current_pos)` 또는 `_first_anchor_from_position(anchors, search_from)` 사용.  
  - 스킵 시에도 "search_from 유지 + search_from 이상 첫 앵커"로 통일할지, 아니면 "next_pos 예측 가능 앵커"(방식 B)로 할지 문서에 한 줄 남겨 두기.
- [ ] **가설이 "예측 가능 기준"을 스킵에만 쓰는 경우** (예: freq518_win50):  
  - 스킵: `anchor_for_next = next_pos - 8` (윈도우 9), 그에 맞는 인덱스.  
  - 정답/오답: `search_from` 갱신 + `_first_anchor_from_position(new_anchors, new_search_from)`.

### 3.3. 윈도우/가설별 상이점

- [ ] **윈도우 크기가 하나인 가설** (예: 윈도우 9만):  
  - 방식 B 식이 단순함: `anchor_for_next = next_pos - (window_size - 1)`.  
- [ ] **여러 윈도우**를 쓰는 가설:  
  - 방식 B는 "해당 position을 **어떤 윈도우로라도** 커버할 수 있는 앵커"가 되므로, `anchor + max_ws - 1 >= position` 형태로 구현.  
  - 기존 문서 [라이브게임_V3_다음앵커_로직_차이.md](./라이브게임_V3_다음앵커_로직_차이.md) 참고.

## 4. 자주 나오는 이슈와 원인

| 증상 | 원인 | 해결 |
|------|------|------|
| `cannot access local variable 'search_from' where it is not associated with a value` | 스킵 분기(또는 어떤 분기)에서 `new_state["search_from"] = search_from` 를 넣었지만, **그 분기 안에서 search_from을 할당하지 않음** | 해당 분기 상단에 `search_from = state.get("search_from", state.get("current_pos", 0))` 추가 |
| 스킵 후 앵커가 잘못 바뀜 | 스킵 시 "다음 앵커"를 방식 A로만 계산해 버림 (search_from 유지인데 _first_anchor_from_position(..., search_from)만 쓰면, 그리드가 늘어나도 앵커가 안 바뀌어야 하는데, 잘못 구현하면 바뀜). 또는 반대로 "다음 예측 위치" 기준(방식 B)이어야 하는데 방식을 섞어 씀 | 가설 규칙에 맞게 "스킵 시에는 방식 B", "종료 조건 충족 시에는 방식 A" 등으로 문서화하고, 한 분기 안에서는 한 방식만 사용 |
| cold_start와 live_step의 다음 앵커가 다름 | cold_start는 보통 방식 A만 사용, live_step은 스킵에 B를 쓰는 경우 있음. 동일 position에서 "다음 앵커" 정의를 두 구현에서 다르게 쓰면 불일치 | 가설별로 "cold_start / live_step 스킵 / live_step 정답·오답" 각각 어떤 방식을 쓰는지 이 문서나 가설 규칙 정리 문서에 적어 두기 |

## 6. 요약

- **방식 A**: "위치 `from_pos` 이상인 첫 앵커" → `_first_anchor_from_position(anchors, from_pos)`, `search_from` 과 함께 사용.
- **방식 B**: "특정 position을 예측할 수 있는 첫 앵커" → 윈도우 9면 `anchor_for_next = next_pos - 8` 후 인덱스 검색.
- **live_step**에서는 **모든 분기**에서 `new_state`를 채울 때 `search_from`을 **반드시** 설정하고, 사용하려면 그 분기 안에서 한 번은 `search_from`을 state에서 읽어 할당해야 함.
- 새 라이브게임 구현 시: (1) 앵커 선택을 **방식 A/B 중 무엇을, 어느 분기에서 쓸지** 먼저 정하고, (2) 위 체크리스트로 각 분기와 상태 변수를 점검하면 재발을 줄일 수 있다.
